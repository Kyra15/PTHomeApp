# Decision record — task 2.4: sensor library for live tracking

**Status:** provisional — confirm with a real-device run (steps below), then change to *accepted*.
**Date:** Oct 2026

## Question
Can a JS-side sensor library deliver accelerometer + gyroscope data fast and steadily enough for rep
counting and ROM (plan §0.5: 50–100 Hz), or do we need a custom native Swift module that forwards
Core Motion into JS?

## Options considered
| Option | Notes |
|---|---|
| **`expo-sensors`** (Accelerometer, Gyroscope) | Already a dependency; maintained with the Expo SDK we're on; wraps Core Motion; `setUpdateInterval(ms)` per sensor; works in dev builds and Expo Go. |
| `react-native-sensors` | Named in the plan. RxJS-based; adds a dependency and native linking, and has been far less actively maintained than the Expo SDK modules. No capability we need that `expo-sensors` lacks. |
| Custom Swift module (Core Motion → JS events) | Most control (e.g. batching, `CMDeviceMotion` gravity/attitude). Only worth the setup cost if the measured rate/jitter below fails. |

## Decision
Use **`expo-sensors` at 50 Hz** for both sensors, streaming together for the whole session
(`src/hooks/useExerciseEngine.ts`). Keep the custom native module as the documented fallback.

Why 50 Hz and not 100: human-speed rehab movements are well under 5 Hz, so 50 Hz is ~10× oversampled;
the accelerometer is low-pass filtered (~6 Hz) before computing tilt anyway. 100 Hz doubles bridge
traffic and battery cost for no measurable gain in rep counting. The engine throttles React re-renders
to ~12/s so the higher sample rate doesn't cost UI smoothness.

## How it's measured (do this on the iPhone)
1. Run the app on a real iPhone (`npx expo run:ios --device` or a dev build). Simulators have no motion sensors.
2. Dashboard → tap your initials → **Check motion sensors**.
3. Lay the phone on a table, tap **Test 50 Hz**, then **Test 100 Hz** (10 s each). Screenshot the results.
4. Pass criteria: achieved rate ≥ 90% of requested for **both** sensors, max gap < 100 ms.
5. Also do one real exercise session: the live screen shows the achieved Hz, the Metro console logs
   `[sensors] accel N Hz, gyro N Hz` every second (dev builds), and the saved session stores
   `accel_hz` / `gyro_hz` in `exercise_logs.summary`.
6. Background the app mid-exercise (swipe home), come back: it must show **Paused** and resume with the
   rep count intact.
